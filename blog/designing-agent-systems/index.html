Field notes · Agent systems

It Forgets Everything.
It Sometimes Lies.
Build Around It.

June 2026·Prannay Hebbar·14 min read

The model is the most reliable part of your agent. Everything you wrap around it is where the failures live, and almost every failure traces back to two defects you can design for.

We keep talking about agents as if the work is making the model smarter. It isn't. The frontier model is the one component you didn't build and can't fix, and it is improving on its own schedule. The part you actually own is the system around it: the memory, the tools, the orchestration, the files on disk. That is where reliability is won or lost.

The two defects: an agent forgets everything between sessions, because its context window is wiped each time. And it sometimes acts with total confidence on something false, because a language model fails by lying, not by crashing.

Neither defect yields to a better prompt. Forgetting is beaten before the action, by designing the world the agent wakes up in. Lying is beaten after the action, by designing the system that catches what slips through. Everything below is one of those two moves.

Part one · Tolerate the failure you can't prevent

01Picture a factory, not a brain

Stop imagining your agent as a brain you prompt. Imagine a small factory of workers passing notes. The orchestrator hands a note to the model, the model asks for a tool, the tool writes to memory, a sub-agent reports back. Every note between workers can be lost, delayed, duplicated, or arrive out of order, and one worker, the model, can hand back something that is fluent and wrong.

This is the most useful reframe in agent engineering: a multi-agent system is a distributed system, and it inherits every failure mode of one. The defining trait of distributed systems is partial failure, and partial failure is nondeterministic. You often cannot tell whether a step succeeded.

Figure 2: Every arrow is a place a note can go wrong. A tool call that times out is the canonical example: the request was lost, or it ran and the reply was lost. The absence of an answer tells you nothing.

The reframe cuts the other way too: do not build the factory before you need it. Architectures get rebuilt at every order of magnitude of load, and the systems crowd has a sharp jab for premature scale, a famous paper asking whether your cluster beats a single laptop. The agent version: don't fan out to five sub-agents what one context window holds. Every worker you add buys some parallelism and pays for it in coordination, and coordination is where every bug in this part of the essay lives.

02The log is the truth; everything else is a cache

The simplest database is a file you only append to. Every index on top of it is derived structure that makes reads faster and writes slower. The same holds for an agent's memory: the append-only trace of what happened is the source of truth, and the summaries, the vector index, and the entity graph are rebuildable caches sitting on top of it.

The operational rule that falls out: never edit history in place. When a fact changes, you append a new entry, you do not overwrite the old one. An agent learns the user lives in Berlin; months later they move to Paris. Overwrite the Berlin fact and you have destroyed the history and the reason. Append "as of June, Paris" and you can still replay, debug, and rebuild every cache from scratch.

Deletion gets the same treatment. If two memory stores merge by keeping whichever record has the newest timestamp, acknowledged facts silently vanish. If they merge by union, deleted facts rise from the dead: Amazon hit exactly this with shopping carts, where removed items kept reappearing because the merge had no record that the removal ever happened. A retraction must be a first-class entry in the log, a tombstone, not merely the absence of a fact.

Figure 3: Lose a cache and you rebuild it from the log. Lose the log and you have nothing. So summaries are disposable; the trace is sacred.
Three bugs the log rule deletes
  1. The dual write. The agent updates the memory store and the search index as two separate writes. One succeeds, one fails, and the two views now disagree forever, silently. Append one event; derive both views from it.
  2. The missing fact that isn't. The agent writes a fact, immediately queries the vector index, finds nothing, and concludes the fact is unknown. The index is an asynchronous follower, and its lag has no upper bound. Reads about your own recent writes must go to the source of truth.
  3. The diverging replay. Syncing state by re-running steps fails the moment a step is nondeterministic, and an LLM call is the most nondeterministic operator you will ever ship. Replicate effects, never re-execute the reasoning.

The truth is the log. The database is just a cache of a subset of the log. Pat Helland, paraphrased

03Silence is not failure

When a tool call times out, you genuinely cannot tell whether it worked. Maybe the email sent and only the confirmation was lost. So you cannot treat "no response" as "didn't happen." The fix is the most important reliability primitive in agent systems: stamp every action with a unique ID, and have the receiver ignore an ID it has already processed. Now a retry is safe, because doing the thing twice has the same effect as doing it once. That property has a name, idempotency, and it is the difference between a retry that heals and a retry that double-charges the customer.

Retries are sharp in four specific ways: the success acknowledgement can be the thing that gets lost (the idempotency key covers this), retries pile load onto an already-struggling system (so back off, and budget them), only transient errors are worth retrying at all, and any side effect that escapes your boundary, the email, the trade, the message, fires on every attempt. Underneath all four sits what atomicity actually means, which is not speed but abortability: a failed attempt must discard its partial effects so the retry starts clean. Retry on top of a half-applied step and you are compounding damage, not healing it.

04One owner, one token

The most common coordination bug in multi-agent systems is the check-then-act race. An agent checks "is task #5 unclaimed?", sees yes, and claims it. But between the check and the claim, another agent did exactly the same thing. Both now believe they own task #5. Per-action atomicity does not save you, because the two actions touched different records and individually each was fine.

The fix is a fencing token. The thing that grants ownership also hands out a number that increases on every handover, and the shared resource obeys only the highest number it has seen. An agent that paused mid-task, for a long model call or a slow tool, and now believes it still holds the lease, gets rejected the instant a newer owner exists. The agent's belief is never authoritative. The resource decides.

Figure 4: "Exactly one orchestrator owns this task" is a coordination problem, not a prompting problem. You solve it with a token the resource checks, not an instruction the agent is asked to honor.

There is a subtler race the token does not catch, because the two writers never touch the same record. Two agents each read "budget remaining: $80," each spend $60 on different line items, and the books now show $120 spent against an $80 limit. Every individual write was atomic; the invariant died anyway. Database people call it write skew, and its general form is the most agent-shaped bug there is: a decision built on an outdated premise. An agent's plan is a snapshot of the world at observation time, and every second of thinking and tool latency widens the gap between premise and world. The fix is mechanical, not clever: re-validate the precondition immediately before committing the side effect, never at planning time.

And sometimes the right move is to not coordinate at all. The alternative strategy has a name, memories, guesses and apologies: act optimistically, detect the rare conflict after the fact, and run a compensation flow, the refund, the correction, the apology email. You need that flow anyway, because the physical world violates your invariants regardless of your locks. If a conflict is cheap to apologize for, optimism plus compensation usually beats synchronous coordination on both cost and latency.

05Grade the end, and watch the tail

Every step returning "OK" does not mean the result is correct. Errors compound across ten steps, and a chain of green checkmarks can still produce a wrong answer. This is the same discipline good agent evals enforce: you verify the final outcome against what the user actually wanted, not just that each tool returned a 200. Read the transcripts; the per-step status was never the thing you cared about.

Most of the bugs that decide that final outcome live in code you have never executed: the error-handling paths. They only run on the night they matter, unless you run them on purpose. So break your own pipeline deliberately: inject a malformed tool output, a truncated model response, a timeout at the worst moment, and watch whether recovery actually recovers. A failure path you have never exercised is not a failure path, it is a hope.

And there is a speed trap hiding in fan-out. If you dispatch five sub-agents and wait for all of them, your latency is the slowest one, not the average. The slow case, the 99th percentile, stops being rare: with enough parallel calls it lands on almost every request. Tail latency is not an edge case in an agent system. It is the common case wearing a disguise.

Figure 5: Four agents finish fast and wait; one straggler decides everything. With fan-out, the orchestrator's median is roughly the p99 of a single sub-agent. Aggregate histograms, never averages of percentiles.

06A prompt edit is a config push

Replication protects you from independent faults: one worker dies, the others carry on. It does nothing against correlated ones, and almost everything interesting about an agent fleet is correlated. Every agent runs the same prompt, the same model version, the same tool schemas. A bad edit to any of these is not one flaky node. It is a fault in every worker at the same instant, the same shape as the leap-second bug that hit thousands of kernels in one night.

Figure 6: Redundancy averages out independent faults. A shared prompt, model version, or tool schema is a single fault domain spanning the whole fleet.

The outage studies are blunt: hardware causes 10 to 25 percent of incidents, and operator and configuration error leads the list. Your prompts are configuration. So give a prompt edit the discipline any config push gets: version it, canary it on a slice of traffic, diff the outcome metrics against the old version, and keep a one-command rollback. Editing the system prompt straight in production is the deployment practice the rest of the industry abandoned twenty years ago.

Part two · Design a world where failure rarely starts

07The operator forgets everything

The knowledge needed to operate anything lives in two places: in the head, what you remember, and in the world, what the thing itself shows you. Good design pushes knowledge into the world so you do not have to hold it in your head. A light switch laid out like the room it controls needs no manual.

An agent takes this to the limit, because its head is erased between every session. Anything it figured out last time is gone unless it was written somewhere durable. So the rule is not an aesthetic preference, it is survival: if it is not in a file, it does not exist tomorrow. Externalize every decision, every convention, and above all every why. And prefer one fact per file over one giant file, so that partial knowledge can be retrieved without dragging everything into a finite context window.

08The environment is the conceptual model

An agent infers how your project works entirely from what the project shows it: directory names, the README, the instruction files. That surface is its mental model, so the surface has to carry its weight.

Two consequences. First, directory layout is not housekeeping, it is documentation: ingest/ transform/ serve/ teaches the data flow on sight in a way that utils/ misc/ stuff/ never can. Second, and less obvious, stale docs are worse than no docs. With no documentation an agent proceeds carefully; with wrong documentation it proceeds confidently in the wrong direction, because it is acting on a false image with full conviction. Fix drift the moment you see it, or delete it.

Distance is the last lever. The stove knob nearest a burner should control that burner, and the file nearest a module should be the one that explains it. Co-locate what changes together: tests beside the code, config beside its service, a skill's reference material inside the skill's own folder. Proximity is the relationship. And keep one name per concept across every layer. When the CLI says deploy, the docs say publish, and the repo says ship, each rename across a boundary is a translation the agent must carry in the one resource it cannot spare: working memory.

09Index everything; put the trigger on the surface

You cannot use what you cannot find, and an agent will not load fifty files to discover that one of them is relevant. So every collection gets an index: one line per item, each with a hook saying when it matters. The index stays loaded; the items are fetched on demand. Names should predict contents before the file is opened, and flat-with-prefixes beats deep nesting, because every directory level is another round trip.

The same logic governs how you describe a tool or a skill. The agent decides whether to open it from its one-line description alone, so that line is a signifier: the visible cue that an action is possible. Write it as a recognition cue, not a summary. use when the deploy fails beats covers deployment, because agents recognize a matching situation far more reliably than they recall a topic.

10Make wrong states unrepresentable

The strongest prevention is not better instructions. It is making the wrong action impossible. A three-prong plug cannot enter the socket backwards, so nobody documents which way to insert it. The error is not prevented; it is unrepresentable. Four kinds of constraint do this work in an agent's environment.

Physical · schemas

Typed tool arguments and validators bounce a malformed call before it spreads. The strictest constraint, and the cheapest to enforce.

Cultural · conventions

The same layout, naming, and commands across every project. The agent learns the rules once and reuses them everywhere for free.

Semantic · names

A directory called archive/ says "do not edit me" with no rule file. The name itself carries the policy.

Logical · invariants

"Every index entry has a file" turns a missing file from a shrug into a detectable error. Absence becomes information.

The corollary for instructions: a template constrains better than prose. A skeleton with holes to fill is a physical constraint on the output's shape; a paragraph describing the desired output is a polite request. Give a form, not an essay.

11The two gulfs

Between an operator and any system sit two gulfs. The gulf of execution is figuring out how to do the thing. The gulf of evaluation is figuring out whether it worked. Good design builds a bridge across each, and an agent crosses both on every action.

Figure 8: Document every project verb as a copy-pasteable command, and make every action produce something verifiable. Without the bottom plank, silent success and silent failure are indistinguishable.

This is where the two halves of the essay meet: the gulf of evaluation is exactly what end-to-end verification bridges. An action with no observable result is a guess, and an agent that gets no signal will march confidently in the wrong direction, exactly the failure mode evals exist to catch.

12Slips versus mistakes

Two kinds of error look identical in a postmortem and need opposite fixes. A slip is the right intention executed wrong: the agent meant the correct path and fumbled it. A mistake is the wrong intention from a bad mental model: it did the wrong thing with full confidence because it misunderstood the situation.

Figure 9: When an agent confidently does the wrong thing, that is a mistake, and the fix is the document that gave it the wrong picture, not a patch on the one incident. Slips are mechanical, so automate the catch.

Two corollaries make errors cheap. Put forcing functions on destructive operations and keep everything reversible, git on everything, so undo always exists. And record the why, not just the what, because the reason is the part that generalizes to the next situation; the patch only fixes this one.

Part three · How they compose

13Prevent at the boundary, tolerate past it

Put the two halves on a single timeline around one agent action and they stop being separate ideas. Everything before the action is prevention: knowledge in the world, constraints that make wrong states unrepresentable, signifiers that point the agent at the right move. Everything after the action is tolerance: idempotency so a retry is safe, a fencing token so a stale agent is rejected, end-to-end verification so you know it worked, an append-only log so nothing is silently lost.

Figure 10: Defense in depth, the Swiss-cheese model applied to agents: prevention reduces how often a fault starts, tolerance keeps the faults that slip through from becoming a wrong final answer.

The hinge is the difference between a fault and a failure. A fault is one component deviating from spec; a failure is the user seeing a wrong result. You cannot drive the fault rate to zero, the model will sometimes be wrong, so the entire job is to stop a fault from becoming a failure. Prevention lowers how often faults start. Tolerance stops the ones that do from reaching the user. Neither half alone is enough.

14Memory outlives the agent

One more rule only shows up with time: data outlives code. The notes your agent writes today will be read by an agent version that does not exist yet, running a model that has not shipped, against formats you have not designed. Two compatibilities follow. Backward: new agents must read old records. Forward, the harder one: old agents must survive records written by newer ones, which means tolerating fields they do not understand.

The classic trap is the round-trip bug. An agent reads a memory record, understands half the fields, rewrites the record, and silently drops the half it did not parse. Any agent that edits memory it only partially understands has this bug, so preserve unknown fields explicitly. And when the format truly must change, do not migrate in place: replay the log into a new view beside the old one, compare them, then switch. The log makes that a routine operation. In-place migration makes it a heart transplant.

15Don't blame the agent

"Human error" is usually a design failure wearing a disguise: the door had no handle, the stove had no mapping, the knowledge was trapped in someone's head. The same is true of agents, and it is the most useful instinct to build.

When an agent flails, it is almost always the environment failing to put knowledge in the world, or the system failing to tolerate a fault it could have. Design the world, design the system, and the agent gets it right by default.

This is also why the frame matters commercially. The model is commoditizing; capability is converging and getting cheaper every quarter. The durable engineering, the part that compounds and is hard to copy, is the system around the model: the memory substrate, the verification layer, the environment design. The teams that win will not be the ones with a marginally better prompt. They will be the ones who treated the agent as one unreliable, amnesiac component and built the scaffolding for it.

Where this came from: nearly everything above is distilled from two books written before LLMs existed. The tolerance half is Martin Kleppmann's Designing Data-Intensive Applications (2017); the prevention half is Don Norman's The Design of Everyday Things (1988). Read them.
